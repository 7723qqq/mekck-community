# 功能实现口径 —— 每个功能该走哪个上游机制

**状态：现行。改动前应读。**

这份文档回答一个问题：**某个功能要做，应该用 Mek（或 AE2 / 原版）的哪个现成机制？**
它不是现状描述，是**约束**。新增机器、改界面、加交互之前先读这里；与这里冲突的实现按这里改。

**唯一总原则：能用上游原生的，一律用原生的。**
自研只在确无对应物时才允许，且必须在代码注释里写明「上游没有对应物」的理由。

背景：本模组历史上大量功能是自研的（自研侧配、自研升级窗、自研 tab、自研槽位视图）。
这些不是设计选择，是历史遗留。用户口径：**「本身就应当是 mek 的，我什么时候允许是自研了」**。

## 一、机器基类 —— 一切的地基

| 该用什么 | 上游类 |
|---|---|
| 机器方块实体 | `mekanism.common.tile.base.TileEntityMekanism` 的子类 |
| 本模组工厂家族基类 | `machine/MekCkMachineTile`（`extends TileEntityConfigurableMachine`） |
| 容器 | `mekanism.common.inventory.container.tile.MekanismTileContainer<TILE>` |
| 屏幕 | `mekanism.client.gui.GuiConfigurableTile<TILE, CONTAINER>`（单机）/ `MekCkFactoryScreenBase`（工厂） |

**为什么必须这样**：`TileEntityMekanism` 的构造器里会回调一批 `getInitial*`，Mek 用它们建好
`TileComponentConfig`（侧配）、`TileComponentUpgrade`（升级）、`TileComponentEjector`（弹出）、
`TileComponentSecurity`（安全）、`TileComponentRedstone`（红石）。**不继承它，这些组件一个都没有**，
只能自己造一套 —— 就是本模组现在的样子。

### 构造期陷阱（踩过两次，写在这里防第三次）

`getInitial*` 系列在**父类构造器内部**被回调，那一刻子类的字段初始化器**还没跑**。所以：

- 子类里凡是 `getInitial*` 要读的字段，**不能写成字段初始化器**，必须在 `getInitial*` 里赋值；
- 执行器 / 缓存这类要读子类字段的东西，**懒加载**（`machine/MekCkMachineTile.java:157-168` 就是这么做的）。

## 二、从 AE 拉料

### 2.1 两条路，别混

| 路 | 触发 | 落点 | 入口 |
|---|---|---|---|
| **A. 手动 / 自动补料** | 玩家点「网络拉料」tab，或勾了「自动补料」 | 机器**输入槽** | `ae2/INetworkPullable` + `MekckAe2.pullNetworkInputs` |
| **B. ME 终端下单** | 玩家在 ME 终端下样板 | 机器**端口窗口** | `pushPattern → insertIntoMachine → insertIntoPortWindow → startOrder` |

### 2.2 路 A：`INetworkPullable`

`ae2/INetworkPullable.java` —— **不引用任何 AE2 类**，AE2 交互全部经 `MekckAe2` 反射门面。
未装 AE2 时接口照常存在、只是没人调。

必须实现：

| 方法 | 含义 |
|---|---|
| `getNetworkPullable()` | 机器方块实体本身 |
| `getNetworkPullInputs()` | 当前**可处理**配方所需材料（`List<AE2InputSpec>`） |
| `getInputSlotRange()` | 输入槽区间 `[start, end)` |
| `getNetworkPullItems()` | 机器的 `ItemStackHandler` |
| `supportsAutoPull()` | 是否支持勾选持续补料 |

可选覆写：

| 方法 | 用途 |
|---|---|
| `getExtraInputSlots()` | 输入槽**不连续**时用（联动机器是 `0..4 ∪ 10..13`，5..9 是产物/升级/电力槽） |
| `isMeOrderEnabled()` / `setMeOrderEnabled()` | ME 终端下单总开关 |
| `getAutoPullStackLimit()` | 自动补料单种材料上限 |

**GUI 侧**：tab 走 `client/MekCkPullTab`（`extends GuiTabElementType<BlockEntity, PullTab>`，**零覆写**，
结构照抄 Mek 的 `GuiBoilerTab`），由 `client/NetworkPullButton.register(gui, pos)` 挂上。
**不要**自己写 tab 类、自己画图标框 —— `GuiTabElementType` 已经把 holder / button / 图标三层 blit 全接管了。

> ⚠️ **自导入坑**：`MekCkPullTab` 类头的类型参数 `PullTab` 不在类体作用域，必须在文件里写
> `import cn.ism.mekck.client.MekCkPullTab.PullTab;`（Mek 的 `GuiBoilerTab` 第一行就是这么干的）。
> 不加报「找不到符号: 类 PullTab」。

### 2.3 路 B：端口声明

新 tile（6 个工厂家族 + 电力烧烤架）**不实现 `INetworkPullable`** —— 它们没有 `ItemStackHandler` 存储区，
输入槽是 Mek 的 `IInventorySlot`。所以路 A 对它们**没有落点**，自动化全部走路 B：

```
ME 终端下样板
  → pushPattern
  → insertIntoMachine          （MekckAe2.java:1902）
  → insertIntoPortWindow       （MekckAe2.java:1955，逐种材料先问 MekPortWindow.bulkSpace 再按量插）
  → startOrder                 （设订单，机器开始加工）
```

机器侧只需实现 `machine/ports/IMekCkPorted`，声明自己的输入段 / 输出段。
`MekckAe2.autoWindow(be)`（`MekckAe2.java:903`）会从 `IMekCkPorted` 拿到 `MekPortWindow`。

### 2.4 缺口状态（2026-10-05 核实并更正）

**原记的「新 tile 不实现 `INetworkPullable`」这一缺口已经关闭**，本节此前的内容已过时：

- `MekCkMachineTile:123` **已 `implements INetworkPullable`**，工厂家族的
  「网络拉料」「自动补料」两枚 tab 已由 `MekCkFactoryScreenBase` 挂回；
- 面板 ME 下单的入口 `pullGenericIngredients` 门禁就是 `instanceof INetworkPullable`，
  随基类补齐后自动生效。

**仍然存在的缺口（如实记，别当已解决）**：`MekckAe2` 里仍有一批按**旧 BE 类型**
派发的 `instanceof` 分支（`FactoryGridHost.getItems()` / `getOutputSlots()` /
`getReturnSlots()` 等）。每台机器迁到 Mek 原生体系时，它对应的分支必须**删除**
（与切菜机 / 电力烧烤架 / 各工厂家族迁完时的处理一致），而不是留着——
留着会让后来者误以为那条路还活着。样板迁移（电力研磨机）在
`MekckAe2` 里删掉了 4 处这样的分支。

## 五、槽位视图（悬浮窗）

| 该用什么 | 上游类 |
|---|---|
| 窗口 | `mekanism.client.gui.element.window.GuiWindow` |
| 打开窗口的 tab | `mekanism.client.gui.element.tab.window.GuiWindowCreatorTab` |
| 窗口里的槽 | `mekanism.common.inventory.slot.VirtualInventoryContainerSlot`（本模组用 `machine/MekCkSlot`，`extends BasicInventorySlot`） |

**本模组实现**：`client/MekCkSlotWindowTab`（`extends GuiWindowCreatorTab<MekCkMachineTile, MekCkSlotWindowTab>`）
+ `client/MekCkSlotWindow`（`extends GuiWindow`）。

**内容分组**（`MekCkSlotWindowTab.buildGroups`）：

- 高档工厂（>17 并行：烈焰炽焱 25 / 晶钛矩阵 36 / 星云塑造 49 / 奇点创世 81）：两组 —— 输入 9 列 + 输出 9 列，并排一页，**不翻页**
- 烹饪 / 穿串：一组 —— 存储（144 / 81 格）
- 其余家族三组都空 ⇒ 屏幕不加这个 tab

**窗口身份必须共享**：输入 / 输出 / 存储三类槽共用 `MekCkMachineTile.SLOT_WINDOW` 一份 `SelectedWindowData`。
`VirtualInventoryContainerSlot.exists(windowData)` 是按身份过滤的，身份不一致就会出现
「窗口里看得见、shift-click 却进不去」。而且 `WindowType.UNSPECIFIED` 的 `maxData == 1` ⇒
两个 UNSPECIFIED 实例**必然相等**，拆成两个常量只是自欺欺人。

> ⚠️ **已知问题（用户报「乱七八糟的的栏位」）**：81 并行的工厂会一次铺开 81 输入 + 81 输出 = 162 格，
> 窗口尺寸与可读性都成问题。**待定**：是否改成 Mek 的翻页 / 分组显示，或按并行档位限制窗口格数。

## 十一、注册

**口径：走 Mek 的注册器，不走原版 `DeferredRegister`。**

| 该用什么 | 上游类 |
|---|---|
| 容器类型 | `mekanism.common.registration.impl.ContainerTypeDeferredRegister` |
| 方块实体类型 | `mekanism.common.registration.impl.TileEntityTypeDeferredRegister` → `TileEntityTypeRegistryObject<TILE>` |
| 方块 | `mekanism.common.block.BlockTypeTile.BlockTileBuilder` |

> ⚠️ **三件套必须成组 `register(bus)`**：`ContainerTypeDeferredRegister` / `TileEntityTypeDeferredRegister` /
> `BlockDeferredRegister` 建好之后**必须在构造函数里 `register(bus)`**，漏一个就是运行期
> 「注册表里没有这个 id」。电力烧烤架迁移时就漏过一次（已补在 `UniversalCuttingMachine.java:1541-1543`）。

**注册名与语言键不许改**（`mekck:electric_grill` / `block.mekck.electric_grill`）——
改了旧存档的方块会变成空气。

### 12.4 样板迁移带出的、每台都要照做的清单

电力研磨机这一台暴露了「迁移」实际要动的东西，比原以为的多。**每台机器都要过这一遍**：

| # | 动作 | 为什么 |
|---|---|---|
| 1 | 新建 `machine/<family>/XxxTile extends TileEntityConfigurableMachine` | 无档位单机**不能**用 `MekCkMachineTile`（那是工厂家族基类，`createExecutor()` 抽象） |
| 2 | 方块换 `BlockTile` + `BlockTypeTile.blockTypeFor(...)` | 属性一个都不能少：`withGui` / `withEnergyConfig` / `withSupportedUpgrades` / `AttributeStateFacing` / `ACTIVE` / `REDSTONE` / `SECURITY` / `INVENTORY` |
| 3 | 注册换成 Mek **三件套**，且构造函数里成组 `register(bus)` | 漏一行 = 运行期「注册表里没有这个 id」，且**编译通过** |
| 4 | **补战利品表** | `BlockTile` 的掉落走战利品表，而旧机器是 `onRemove` 自行掉落。**漏了就是破坏后什么都不掉** |
| 5 | 菜单换 `MekanismTileContainer`，删手写槽类与 `ContainerData` | 槽由 `addSlots()` 从 tile 自动装配；读数改 `addContainerTrackers` 同步通道（**不再有 16 位截断，`WideDataSlot` 那套随之作废**） |
| 6 | 屏幕换 `GuiConfigurableTile`，**删掉自摆的侧配/升级/红石 tab** | Mek 自己会挂；留着就是两套 tab 叠在一起 |
| 7 | 屏幕补 `drawForegroundText` | 不覆写 ⇒ 机器名与「Inventory」标签**一个都不画**（Mek 的 `renderLabels` 不调 super） |
| 8 | 删 `MekckAe2` 里本机的 `instanceof` 分支 | 留着会让后来者以为那条路还活着 |
| 9 | 旧的 `SideMode` / 升级槽 / 创造槽槽位随体系消失，槽下标会**变** | 新槽序（如研磨机 `[输入, 输出, 能源]`）是**新的存档契约**，要与战利品表、迁移器对齐 |
| 10 | 更新护栏里的登记表 | 见 §12.5 |

### 12.5 护栏登记表（每台迁完都要同步的地方）

源码形态护栏会**成批变红**——这是设计意图，不是故障。样板迁移改红了 17 条断言，
分三类处置，**没有一条是靠放宽判据通过的**：

| 类别 | 处置 | 例 |
|---|---|---|
| **真缺陷被我引入** | 改代码，不改判据 | 战利品表缺失（`TestFactoryLootTableSustainData`）、屏幕不画标签（`TestGuiInventoryLabels`） |
| **判据对象随迁移消失** | 改判据的落点，断言的东西不变 | `getMachineFacing()` 随朝向交给 Mek 而消失；`UpgradeSlot` 随升级交给组件而消失 |
| **登记表/阈值随迁移收缩** | 同步收缩，并在注释里写明理由 | `MENUS` 表、`POWER_SLOT_TARGET_*`、`KNOWN_VIOLATIONS`、`KNOWN_MIGRATION_DEBT`、`seen >= N` 阈值 |

> ⚠️ **最后一条最危险**：这些「发现缺口的自检」（如 `checked >= N` / `seen >= N`）
> 正是防止判据空转的机制。收缩阈值时**必须在注释里写出「N → N-1」与原因**，
> 否则下一个人无法区分「正常收缩」与「有人为了让红灯变绿而放宽了判据」。
